Both sides appended to the end of an append-only JSONL ledger and neither

| Side | Lines | Added |
|---|---|---|

| 104 run branch | 78 | 105 `failed-criterion`, 106 `failed-criterion`, 104 `failed-criterion`, 104 `verified-by` |

The union is the resolution and the order does not matter to a ledger. The
card itself auto-merged.

This is a harness artefact, not a work defect, and it is **structural**:
`memory/facts.jsonl` is written by every stage on every landing, so any two
landings that overlap in time conflict on it by construction. Card 84 made
a landing leave a fact behind; nothing made the ledger mergeable. Card 111
("dev moving does not park a disjoint landing") addresses the parking, not
this — two stages with genuinely disjoint path claims still both write the
ledger, so 111 as drafted will hand this same conflict to its
auto-integrate path rather than removing it.

**Improvement:** give `memory/facts.jsonl` a union merge driver
(`.gitattributes: memory/facts.jsonl merge=union`, or a custom driver that
sorts and dedups). One line of config removes an entire class of parked
landing. Without it, card 111 lands an auto-integrator that will refuse on
its first real overlap.

**Improvement:** no context seed is rendered on this host
(`scripts/render-controller-seed.sh` has never been run here), so
`phat-controller.sh --print-seed` returns "the job has not been configured".
An interactive session can work around it; a scheduled `phat-controller
pass` would dispatch an agent with no mandate, no paths and no prohibitions.

## Blocker: the pause parser does not read Codex's wording

`state/budget.json` was paused 10:31:57Z until 11:31:57Z — exactly 3600
seconds, the default fallback. The banner that caused it says:

```
ERROR: You've hit your usage limit. Upgrade to Pro (...) or try again at 3:49 PM.
```

`scripts/usage-limit.sh:80` parses the reset time with

```
r"resets?\s+(?:at\s+)?(\d{1,2})(?::(\d{2}))?\s*([ap]\.?m\.?)?"
```

which requires the literal word `reset`/`resets`. Codex says **"try again
at"**. Measured against the live line:

| Banner | `usage_limit_reset_epoch` |
|---|---|
| `...or try again at 3:49 PM.` (Codex) | *empty* |
| `You've hit your session limit · resets 1:10pm` (Anthropic) | `1788696600` |

Detection is fine — `USAGE_LIMIT_PATTERN` catches the Codex banner and the
pause is correctly a pause, not a stall (card 97 did its job). It is only
the *reset time* that is lost, so the loop backs off for one hour against a
four-hour outage and will resume at 12:31 into a wall it cannot pass until
15:49. The file's own header comment is written entirely around the
Anthropic wording, so the Codex phrasing was never in scope.

**Improvement:** widen the regex to
`(?:resets?|try again)\s+(?:at\s+)?...`, and add both vendors' real banners
as fixtures to `scripts/usage-error-smoke.sh`. This belongs with card 109
("a worker retrying a dead API is not working"), which is already queued and
already owns this area.

## Blocker: every remaining stage has a Codex seat

The batch alternates families by design (cross-family verification), which
means **0 of the 17 pending stages can run without Codex** — it is the
worker on the odd cards and the verifier on the even ones. With the
subscription out until 15:49, four hours of a twelve-hour drain are
unusable unless Codex is re-routed.

API mode is available and configured: the sibling `CODEX_HOME` at
`~/.codex-api-only` exists with `auth_mode: apikey`, and
`OP_REF_OPENAI_API_KEY` resolves to a real ref. `.autometta.local.yaml`
currently reads `auth.codex.mode: subscription`. The flip is one line, or
`AUTOMETTA_CODEX_MODE=api` at dispatch. It is a billing change, so it is the
operator's call, not the controller's.

**Improvement:** the cross-family pairing rule guarantees that one exhausted
provider stops the whole queue, however much headroom the other has. A run
design that alternates seats has no degraded mode. Worth a card: when one
family is paused, allow the queue to reorder to stages whose *worker* is the
live family and hold their verification, rather than pausing the repo.

Claude session limits restored. The operator reports windows burning faster

subscriber:

- daytime, stop the run while more than 20% of the Claude session remains,

- burning the whole daytime session stays possible but opt-in;
- in the overnight window 22:00 to 01:00 the session may be spent to the

The mechanism for the first two already exists and protects nothing.
`quota_reserve_settings` (`scripts/quota-window.sh:33-50`) reads
`window_reserve.percent` / `.action` from the host mandate, and
`quota_gate_reading` holds a dispatch only under `action: hold`, failing
open on unknown, on zero and on `observe`. The live mandate reads
`percent: 10, action: observe`, so every daytime dispatch has logged a
reading and proceeded anyway. The gap is that the reserve is one number with
no sense of time, and that there is no overnight stop in this repo at all —
the 01:00 stop used on emergence-lab on 2026-09-03 was a hand-installed
LaunchAgent that failed to remove itself.

Card 124 makes `window_reserve` schedule-aware, puts the stop in the tick
rather than in an installed job (resumable, killable, nothing left behind),
and makes the daytime burn an opt-in `drain.sh start --ignore-reserve` —
reusing the verb that is already the operator's bounded, self-expiring
"spend the window down on purpose" rather than adding a second switch. An
in-flight stage is never killed by the stop; it finishes and lands.

Seats deviate from the batch rule on purpose. The rule puts Opus on the
worker seat for a high-effort card; here Opus verifies, because the failure
this card must not ship is a guard that silently fails open, and that is
caught by verification rather than by construction. `window_reserve` has
been doing exactly that for weeks.

### Blocker: reordering the queue corrupted state.yaml, and the backup caught it

Moving a stage means editing the `stages` array by hand, and the first
attempt broke the file. 124's record was the last in the array, so a block
that ends "at the next `- id:` line, or end of file" swallowed the three
top-level keys that follow the array — `last_tick_at`, `tick_count`,
`clock_tick_budget_remaining` — and carried them into the middle of the
list. `yq` then refused the file at L2168, and `picture` reported **zero
stages** while the raw file still looked plausible to the eye and still held
104 `- id:` lines.

Restored from the copy taken immediately before the edit, re-done with the
block bounded by the next stage *or the first top-level key*, whichever
comes first. 17 pending, order correct, trailing keys intact.

This is gotcha 10 with a different trigger: the hazard there was a
degenerate read/write leaving an empty `stages: []`; here it was a
structurally valid file whose array had eaten its siblings. The lesson that
held is the cheap one — copy the file before touching it, and re-read it
through the parser afterwards rather than trusting a visual check.

**Improvement:** the queue has no supported way to say "run this next".
`add-stage.sh` appends, and there is no reorder verb, so an urgent card
requires a hand edit of the one file the loop cannot survive losing. A
`queue-card --before <stage-id>` or a controller `reorder` verb would remove
the need to hand-edit `state.yaml` at all.
